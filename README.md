# Orchestration Testing

Одна воспроизводимая задача по агентской разработке и короткий автоматически
сформированный отчёт. Python 3.11+, SQLite и Git; внешние библиотеки не нужны.

## Самый простой запуск

Отправьте агенту:

> Выполни тестовую задачу из https://github.com/Vitykovskiy/orchestration-testing.
> Клонируй репозиторий в новый каталог, следуй AGENTS.md и верни REPORT.md,
> report.json и changes.patch.

Агент запускает измерение, выполняет [задачу](TASK.md) и получает файлы:

| Файл | Для чего |
|---|---|
| `REPORT.md` | Короткий итог для чтения и отправки в чат |
| `report.json` | Метрики, условия, все критерии и ошибки для сравнения |
| `changes.patch` | Результат разработки, включая новые файлы решения |

Файлы сохраняются в `.benchmark/results/<run-id>/`. Каждая новая попытка — новый
clone и новый диалог. Исходная версия приложения намеренно не выполняет часть
требований; базовые проверки её работоспособности проходят.

## Что делает задача

Нужно доработать CLI управления складом: корректно фильтровать склады, безопасно
повторять отмену, реализовать JSON/CSV-экспорт и устойчивые к перезапуску ключи
повторных запросов. В задаче есть связанные изменения и независимые части;
способ делегирования выбирает исследуемая конфигурация агента.

Приёмка проверяет **13 критериев** на свежих базах данных. Проверки открыты.
Это практический тест разработки, а не скрытый экзамен или доказательство
универсального преимущества одной архитектуры.

## Повторяемое сравнение двух версий Toolkit

Для измерения без пауз в чате используйте отдельный чистый checkout стенда
как контроллер. Нужен установленный и авторизованный Codex CLI на Linux/macOS.
Toolkit должен быть клонирован отдельно и содержать обе нужные ревизии.

```bash
python3 bench.py run \
  --toolkit ../codex-toolkit --toolkit-ref <FULL_BASELINE_SHA> \
  --label baseline --model <MODEL> --effort medium \
  --environment-label clean-machine-1 --output ../runs/baseline-1

python3 bench.py run \
  --toolkit ../codex-toolkit --toolkit-ref <FULL_CANDIDATE_SHA> \
  --label candidate --model <SAME_MODEL> --effort medium \
  --environment-label clean-machine-1 --output ../runs/candidate-1
```

Контроллер сам создаёт новую рабочую копию, подключает выбранный commit Toolkit
только в неё, запускает Codex, затем проверяет результат и записывает отчёт.
Существующие проекты и глобальные навыки не изменяются. Лимит по умолчанию —
30 минут на попытку; для обеих групп он должен совпадать.

Сделайте по пять попыток в чередующемся порядке A/B, B/A, A/B, B/A, A/B:
используйте новые каталоги `baseline-2`…`baseline-5` и `candidate-2`…`candidate-5`.
Не отбрасывайте неудачи и тайм-ауты. Затем:

```bash
python3 bench.py compare \
  --baseline ../runs/baseline-*/report.json \
  --candidate ../runs/candidate-*/report.json
```

Получатся `COMPARISON.md` и `comparison.json`. Правило принятия: без ухудшения
успешности и критических ошибок, время на принятую задачу с учётом всех неудач
снижается минимум на 15%. Пять повторов и 15% — инженерный порог, не тест
статистической значимости. [Полный протокол и ограничения](docs/protocol.md).

## Проверка самого стенда

```bash
python3 -m unittest discover -s tests_product -v
python3 -m unittest discover -s tests_harness -v
```

Приёмка исходного незавершённого приложения должна завершиться с ошибкой:

```bash
python3 -I verification/check.py --workspace .
```

Её результат на поставляемой версии — 4/13. Тесты стенда проверяют, что
ошибки обнаруживаются, отчёт не подменяет расход корневого потока расходом
всего дерева, а результат решения можно воспроизвести из patch.
