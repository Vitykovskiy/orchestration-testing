# Orchestration Testing

Набор воспроизводимых задач для оценки агентской разработки: изменений
Codex Toolkit и влияния доступного количества субагентов. Python 3.11+, Git,
стандартная библиотека; сторонние зависимости не нужны.

Для сравнения Toolkit до и после PR #14 есть [готовое задание локальному агенту](docs/experiments/toolkit-ab-2026-10-26.md): точные версии, порядок запусков, лимиты субагентов и состав итогового архива.

## Что проверяем

| Сценарий | Задача | Что можно оценить |
|---|---|---|
| `small` | Узкая правка текстового вывода с сохранением JSON | Цена запуска и лишнего делегирования |
| `workflow` | Исправления, экспорт и повторяемые запросы в складском CLI | Связанные изменения, диагностика, интеграция и ревью |
| `parallel` | Шесть независимых аналитических модулей и общий результат | Выигрыш от параллельного выполнения и стоимость координации |
| `handoff` | Планирование, новая сессия, уточнение требований и реализация | Передача контекста и соблюдение обновлённых требований |

Каждая задача имеет собственные исходники, требования и приёмочную проверку.
Нужное количество исполнителей не предписано. Проверки открыты, эталонные
решения в репозиторий не включены.

## Самый простой запуск: дать ссылку агенту

> Выполни сценарий parallel из https://github.com/Vitykovskiy/orchestration-testing.
> Подготовь новую рабочую копию, следуй AGENTS.md и верни REPORT.md, report.json
> и changes.patch.

Можно выбрать любой сценарий из таблицы; без уточнения выполняется `workflow`.
Агент подготовит нужную копию через `bench.py prepare`, начнёт измерение,
выполнит задачу и сформирует три файла:

| Файл | Назначение |
|---|---|
| `REPORT.md` | Короткий итог для чтения и отправки в чат |
| `report.json` | Условия, метрики, все критерии и ошибки |
| `changes.patch` | Изменённые и добавленные файлы решения |

Для следующей попытки нужна новая копия и новая сессия. В ручном режиме время
включает паузы в диалоге; строгий вывод об ускорении по нему не выдаётся.

## Проверить влияние количества субагентов

Нужны установленный и авторизованный Codex CLI на Linux/macOS, чистый checkout
стенда и отдельно клонированный Toolkit. Одна и та же ревизия Toolkit, модель
и среда используются для всех лимитов. `--subagents 4` означает до четырёх
субагентов **помимо основного потока**, а не требование обязательно запустить четыре.

Сначала можно сохранить только план без вызовов Codex:

```bash
python3 bench.py matrix \
  --toolkit ../codex-toolkit --toolkit-ref <FULL_SHA> \
  --model <MODEL> --environment-label clean-machine-1 \
  --cases small workflow parallel handoff --subagents 1 2 4 \
  --repeats 1 --plan-only --output ../runs/capacity-plan
```

Для технической пробы выполните ту же команду без `--plan-only`, указав новый
`--output ../runs/capacity-pilot`. Это **12 попыток**. Для основной серии
используйте `--repeats 5` и новый каталог: **60 попыток**.
Каждая попытка ограничена 30 минутами (`--timeout 1800`); суммарный лимит работы
Codex в основной серии — 30 часов, подготовка и приёмка идут сверх этого.
Выбирайте только нужные `--cases`, если полный набор
дорог. `handoff` содержит две сессии в пределах общего лимита одной попытки.

Контроллер сам создаёт свежие рабочие копии, подключает выбранный commit Toolkit,
чередует лимиты в зафиксированном порядке и последовательно запускает попытки.
Внутри каждой попытки агенты могут работать параллельно. В конце получаются
**`MATRIX.md` и `matrix.json`**, а также отдельные отчёты и patch каждой попытки.
Новая серия требует нового каталога: результаты не перезаписываются.

## Один управляемый запуск

```bash
python3 bench.py run \
  --case parallel --subagents 4 \
  --toolkit ../codex-toolkit --toolkit-ref <FULL_SHA> \
  --label capacity-4 --model <MODEL> --effort medium \
  --environment-label clean-machine-1 --output ../runs/parallel-4-1
```

Лимит передаётся в настройку Codex; фактический пик одновременно открытых
потоков отдельно не измеряется. Все версии, параметры, лимит и доступная
статистика корневого потока фиксируются в отчёте. Полный расход токенов
субагентов не выдаётся за измеренный.

## Сравнение версий Toolkit и сравнение лимитов

```bash
python3 bench.py compare --study toolkit \
  --baseline ../runs/baseline-*/report.json \
  --candidate ../runs/candidate-*/report.json

python3 bench.py compare --study capacity \
  --baseline ../runs/capacity-1-*/report.json \
  --candidate ../runs/capacity-4-*/report.json
```

`toolkit` требует разные commit Toolkit при одинаковом лимите субагентов.
`capacity` требует одну ревизию Toolkit при разных фиксированных лимитах.
Модели и настройки всех профилей должны совпадать. Результаты разбираются
**отдельно по каждому сценарию и критерию**. Ускорение одной задачи не скрывает
ухудшение другой. Неудачные попытки и тайм-ауты учитываются в затраченном времени.

Для положительного вывода нужно не меньше пяти повторов каждого сценария
на вариант, сохранение качества и минимум 15% экономии времени на принятую
задачу. Это инженерное правило, не доказательство статистической значимости.
Матрица показывает также случаи, где увеличение лимита не помогло.
[Подробный протокол и ограничения](docs/protocol.md).

## Проверка самого стенда

```bash
python3 -m unittest discover -s tests_product -v
python3 -m unittest discover -s tests_harness -v
python3 bench.py cases
```

Исходные приложения намеренно не выполняют часть требований. Приёмка такой
версии должна завершаться с ошибкой; базовые smoke-тесты проходят. Контроллер
проверен на временных исправленных решениях и возврате отдельных дефектов.
Это проверка средств измерения; реальные показатели эффективности появляются
только после запуска вашей серии Codex.
