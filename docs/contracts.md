# Контракты stockctl

Python 3.11 или новее; только стандартная библиотека. Все команды запускаются
из корня репозитория. Состояние хранится только в указанной SQLite-базе.

## Команды

```text
python3 -m stockctl --db PATH init
python3 -m stockctl --db PATH stock add --warehouse W --sku SKU --qty N
python3 -m stockctl --db PATH stock list --warehouse W --format json|text
python3 -m stockctl --db PATH reserve --warehouse W --sku SKU --qty N [--request-id KEY]
python3 -m stockctl --db PATH cancel ID
python3 -m stockctl --db PATH ship ID
python3 -m stockctl --db PATH export stock --format json
python3 -m stockctl --db PATH export movements --format csv
```

`--request-id` и экспортёры входят в требуемый результат задачи; исходная
реализация пока их не поддерживает. `init` создаёт пустую базу; повторный вызов
сохраняет существующие данные. Остальные команды тоже могут открыть старую базу
без предварительного ручного обновления её схемы.

Успех: код завершения `0`, результат в stdout. Ошибка предметной области или
SQLite: код `2`, непустая JSON-строка `{"error": "описание"}` в stderr, stdout пуст.
Ошибки синтаксиса аргументов могут использовать стандартный вывод argparse.
Текст описания ошибки не фиксирован. Некорректная операция не должна менять
товар, резервы или журнал. Порядок ключей JSON и пробелы несущественны.

## Остатки и резервы

Идентификатор позиции — пара `(warehouse, sku)`. Значения непустые; допускаются
Unicode, запятые, кавычки и переводы строк. Количество — положительное целое число.
`on_hand` — физический остаток, `reserved` — занято активными резервами,
`available = on_hand - reserved`. Склады изолированы. Добавление товара увеличивает
только `on_hand` указанной позиции. Недостаток доступного товара — ошибка.

`stock add` возвращает один объект:

```json
{"warehouse":"W1","sku":"SKU-A","on_hand":10,"reserved":0,"available":10}
```

`stock list --warehouse W --format json` возвращает массив таких объектов только
для склада `W`, отсортированный по `sku` в порядке SQLite `BINARY`. Неизвестный
склад возвращает `[]`. Текстовый формат имеет заголовок
`Склад\tSKU\tНа складе\tЗарезервировано\tДоступно` и те же отфильтрованные данные.

Резервирование увеличивает `reserved` на `qty` и создаёт резерв `active`.
Отмена активного резерва уменьшает `reserved` на `qty` и переводит его в
`cancelled`. Повторная отмена возвращает тот же резерв без изменений состояния.
Отгрузка активного резерва уменьшает и `on_hand`, и `reserved` на `qty`, переводит
резерв в `shipped`; повторная отгрузка ничего не изменяет. Отмена отгруженного
резерва, отгрузка отменённого и обращение к неизвестному ID — ошибки.

`reserve`, `cancel` и `ship` возвращают объект с текущим состоянием резерва:

```json
{"id":1,"warehouse":"W1","sku":"SKU-A","qty":2,"status":"active"}
```

ID — положительное целое число, уникальное в базе. Статусы фиксированы:
`active`, `cancelled`, `shipped`. Поле `request_id` добавлять в ответ не требуется.

## Ключ запроса

`reserve --request-id KEY` принимает непустой ключ, уникальный в пределах базы.
Первый успешный запрос сохраняет связь ключа и резерва. Повтор того же ключа с
теми же `warehouse`, `sku`, `qty` возвращает тот же ID и **текущий** статус
резерва, даже если он уже отменён или отгружен. Он не меняет остатки и журнал.
Это действует после завершения процесса и повторного открытия базы.

Тот же ключ с другим складом, SKU или количеством — ошибка без изменений.
Неуспешное резервирование не занимает ключ: после устранения причины его можно
использовать. Вызов без ключа сохраняет прежнюю семантику: каждый успешный вызов
создаёт новый резерв. Пустой ключ — ошибка. Одновременные процессы и внешние
системы в задачу не входят.

## Исходная схема и совместимость

Старая база имеет три таблицы:

| Таблица | Столбцы |
| --- | --- |
| `stock` | `warehouse TEXT`, `sku TEXT`, `on_hand INTEGER`, `reserved INTEGER`; составной первичный ключ `(warehouse, sku)` |
| `reservations` | `id INTEGER PRIMARY KEY AUTOINCREMENT`, `warehouse TEXT`, `sku TEXT`, `qty INTEGER`, `status TEXT` |
| `movements` | `id INTEGER PRIMARY KEY AUTOINCREMENT`, `reservation_id INTEGER NULL`, `warehouse TEXT`, `sku TEXT`, `delta INTEGER`, `kind TEXT` |

В `stock` все поля `NOT NULL`; `reserved` имеет значение по умолчанию `0`.
В `reservations` все поля кроме автоматически назначаемого ID — `NOT NULL`.
В `movements` только `reservation_id` может быть `NULL`.
Внешние ключи: резерв → позиция по `(warehouse, sku)`, движение → резерв по ID.
Новая схема может добавлять необходимые элементы, сохраняя эти таблицы, столбцы,
идентификаторы и данные. Обновление схемы должно быть повторяемым. Для старых
резервов без ключей прежние операции продолжают работать.

Каждая фактическая операция добавляет ровно одно движение; повтор отмены,
отгрузки или успешного запроса с ключом не добавляет движение.

| `kind` | `delta` (изменение физического остатка) | `reservation_id` |
| --- | --- | --- |
| `add` | `+qty` | `NULL` |
| `reserve` | `0` | ID резерва |
| `cancel` | `0` | ID резерва |
| `ship` | `-qty` | ID резерва |

## Экспорт

Экспорт читает все склады и не меняет содержимое базы. Повторный экспорт одного
состояния даёт одинаковый текст. Пустая база — корректный случай.

### Остатки в JSON

Массив объектов с полями ровно `warehouse`, `sku`, `on_hand`, `reserved`,
`available`. Сортировка по `warehouse`, затем `sku` в порядке SQLite `BINARY`.
Пустая база возвращает `[]`. Unicode должен корректно восстанавливаться
JSON-парсером; экранирование Unicode не фиксируется.

### Движения в CSV

Первая строка: `id,reservation_id,warehouse,sku,delta,kind`. Дальше все движения
по возрастанию числового `id`. Разделитель — запятая; поля с запятыми, кавычками
или переводами строк должны корректно читаться стандартным `csv.reader`.
`NULL` в `reservation_id` — пустая ячейка. Пустая база возвращает только заголовок.
Переводы строк `LF` и `CRLF` допустимы. Вывод заканчивается переводом строки.
