# Протокол сравнения

## Что фиксируется

Стенд содержит четыре сценария: `small`, `workflow`, `parallel`, `handoff`.
Зафиксируйте набор сценариев и один commit стенда. В `--study toolkit`
сравниваются разные полные commit SHA Toolkit при одном лимите субагентов.
В `--study capacity` сравниваются разные лимиты при одном commit Toolkit.
Незакоммиченные изменения Toolkit не импортируются. Не изменяйте кандидата
между попытками; изменение кандидата начинает новую серию.

Модель корневого агента, reasoning, версия Codex, лимит времени, доступные
инструменты и ограничения должны совпадать. Модели профилей берутся из выбранного
Toolkit без подмены. Для проверки изменения инструкций их настройки должны
совпадать между A и B. Не меняйте одновременно инструкции и модели.
Отпечаток настроек всех импортированных профилей входит в проверку
сопоставимости; текст описаний и инструкций из этого отпечатка исключён.

`--environment-label` — ваша метка подготовленной среды. Она не создаёт изоляцию.
Запускайте обе группы в одинаковых чистых контейнерах/VM либо в отдельной
подготовленной учётной записи без посторонних глобальных навыков, инструкций,
MCP и hooks. Отдельный `CODEX_HOME` сам по себе не доказывает отсутствие других
путей обнаружения навыков. Контроллер не читает и не публикует ваши секреты
или содержимое глобальной конфигурации. Соответствие среды остаётся условием
эксперимента, а не технически доказанным свойством отчёта.

Лимит `--subagents N` передаётся как
`agents.max_concurrent_threads_per_session=N` и не включает основной поток.
Стенд записывает запрошенную настройку; `observed_peak_subagents = null`.
Он не доказывает фактическую загрузку всех N слотов. Исключите конфликтующие
глобальные переопределения лимита и закрепите версию CLI. Недокументированные
настройки разных реализаций multi-agent стенд не добавляет автоматически.

В сценарии `parallel` шесть независимых модулей, но исполнители выбирают
собственный способ работы. `small` нужен, чтобы увидеть издержки координации;
`workflow` — влияние связности; `handoff` — восстановление по артефактам и
корректное применение уточнения в новой сессии. Результат сценария не является
полной оценкой какого-либо отдельного пакта: на него влияет весь процесс.

## Порядок

1. Выполните по одной технической пробе A и B, чтобы проверить доступность
   моделей, инструментов и запуск. Храните их отдельно от основной серии.
2. Для пары вариантов заранее задайте порядок A/B, B/A, A/B, B/A, A/B. Каждая
   пара использует новую копию приложения, новую сессию и одинаковые условия.
   Последовательный запуск исключает конкуренцию за лимиты одного аккаунта.
3. Не подсказывайте решение, не переносите память диалога, исходники решения
   и предыдущие отчёты в следующие попытки. Не подстраивайте правила под
   неудачный результат внутри серии.
4. Сохраните все отчёты каждого сценария и варианта. Тайм-аут, неполное решение и неудача агента
   остаются в знаменателе качества и в суммарном времени.
5. Запустите `compare`. Разберите каждое расхождение функциональных критериев.
   После доработки Toolkit повторите полную серию с новым SHA.

`matrix` автоматизирует сравнение лимитов: сохраняет порядок и seed в
`matrix-plan.json`, чередует лимиты внутри каждого сценария и запускает
попытки последовательно. Параллельна только работа внутри попытки.
Четыре сценария × три лимита × пять повторов дают 60 попыток. Техническая
проба с одним повтором — 12 попыток; положительный вывод по ней не выдаётся.
`--plan-only` сохраняет план и бюджет без вызова Codex.
Сводка `MATRIX.md` показывает каждый сценарий и лимит отдельно.

Если процесс не запустился из-за отсутствия Codex/авторизации, это техническая
проба, а не завершённая попытка. Ошибка после начала запуска сохраняется как
неуспех. Сбой машины без отчёта нужно явно приложить к журналу серии: программа
не может восстановить отсутствующие измерения. Не удаляйте такие попытки молча.

## Метрики

- Успешность = принятые попытки / все попытки. `accepted` означает выполнение
  публичных функциональных критериев и соблюдение границ изменяемых файлов.
  Это не независимое человеческое ревью и не доказательство соблюдения всех
  внутренних процедур Toolkit.
- Время на принятую задачу = время всех попыток / число принятых задач.
  При нуле принятых задач значение отсутствует, а не равно нулю.
- Внешнее время измеряется от запуска Codex до завершения его процесса,
  включая требуемые ему проверки и исправления. Клонирование, подключение
  Toolkit и последующая независимая приёмка исключены. Агент должен завершить
  всех необходимых исполнителей до своего финального ответа.
  Для `handoff` суммируется время двух отдельных процессов Codex с одним
  общим лимитом; до второй сессии контроллер проверяет наличие плана и отсутствие
  преждевременных правок. Итоговый проверяющий код не пытается восстановить этот
  этап задним числом. В ручном режиме этап фиксирует `checkpoint`.
- В режиме `start/finish` время включает паузы в диалоге. Этот отчёт годится
  для проверки результата и предварительного наблюдения; строгий автоматический
  вывод об ускорении по нему не выдается.
- JSONL `codex exec --json` даёт наблюдаемую статистику корневого потока.
  Покрытие субагентов здесь не подтверждено: `total_tree_tokens = null`.
  Кэшированные входные токены не прибавляются повторно; reasoning не
  прибавляется к выходным токенам. Количество субагентов также неизвестно,
  если оно не измерено. Программа не оценивает стоимость в деньгах или квотах.

`compare` требует пять попыток каждого сценария на вариант, одинаковые условия,
соблюдение выбранного режима сравнения, отсутствие критических ошибок кандидата и снижения успешности,
отсутствие ухудшения каждого отдельного критерия приёмки,
неувеличение числа вмешательств и экономию времени не менее 15%. Недостаточные
или несопоставимые данные дают «эффект не подтверждён».
Наборы сценариев и число попыток должны совпадать. Снижение качества отдельного
сценария или критерия блокирует положительный общий вывод. Общая экономия
рассчитывается только для одинакового состава задач; отдельные ускорения и
замедления видны в таблице. Показатель ускорения — отношение времени на принятую
задачу A/B, а не отношение доступных слотов.

## Проверка отчёта и защита от случайной подмены

`finish` извлекает проверяющую программу из Git commit начала попытки.
Изменение файлов проверок, задания или инструкций отмечается как нарушение.
`changes.patch` включает только разрешённое решение; SHA-256 patch записан
в `report.json`. Нельзя перезаписать готовую попытку командой `finish`.

Для независимой повторной проверки используйте чистый checkout того же commit
стенда как контроллер и готовую рабочую копию решения:

```bash
python3 bench.py verify --workspace /path/to/finished/workspace --output recheck.json
```

Команда повторяет функциональную приёмку; она не восстанавливает затраченное
время, не подтверждает старую метрику и не проверяет неизменность всей среды.
Отдельная проверка границ и patch нужна при разборе подозрительного отчёта.
Git, локальные файлы и открытый проверяющий код не являются защитой от
злонамеренного агента с полным доступом к этой машине. Для строгого слепого
испытания потребуется отдельный доверенный контроллер и закрытые случаи.

После оптимизации по этому открытому набору подтвердите эффект на новой,
ранее не использованной задаче перед общим выводом о Toolkit.

## Источник интерфейса запуска

Команды `codex exec --json`, `--sandbox workspace-write` и
`--output-last-message` основаны на
[официальной документации Codex](https://learn.chatgpt.com/docs/non-interactive-mode).
Требуется доступная пользователю совместимая версия CLI; модель задаётся явно.
Семантика лимита взята из
[официальной документации субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).
